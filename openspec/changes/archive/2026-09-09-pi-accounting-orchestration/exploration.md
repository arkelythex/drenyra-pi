# Exploration: pi-accounting-orchestration

Phase: sdd-explore
Master linkage: SDD-030 (Organic Accounting Work Routing) — README's Drenyra Dominion Program table: "Direct / delegated / durable-mission routing from evidence and risk." Shell's role is scaffolding/serving this master capability, not owning or completing it (same posture as SDD-020 in `pi-operator-onboarding`).
Audited against: dirty working tree, drenyra-shell @ main, 2026-09-09.
Prior ground truth reused, not re-derived: `openspec/changes/archive/2026-09-08-pi-capability-conformance/exploration.md` (BudgetLedger fail-closed behavior, UNKNOWN-state halting, `extensions/register.ts:1186-1190` advisory-only model-routing) and `docs/architecture/capability-conformance-matrix.md` (verification-level scheme, `model-routing` = `unit-or-contract-tested` but advisory-only).

## Current State

**The routing adapter is real, well-tested, and architecturally sound — but it is not wired into any live `/drenyra:*` command today. This is the single most important finding for this change's scope.**

### What exists (`lib/routing/`)

- `lib/routing/types.ts` — `RoutingRoute = "direct" | "delegated" | "durable"` (line 80); `BudgetLedger` class (lines 227-339, already cited in SDD #1) enforces real per-work-unit ceilings (TIME/TOKENS/COST/RESEARCH_ATTEMPTS/CORRECTION), fails closed, never transfers across work units (`assertWorkUnit` throws on mismatch, line 249-255).
- `lib/routing/preflight.ts` — an 8-stage `runRoutingPreflight` (scope → permissions → evidence → materiality → reversibility → systems → approval → routing). Stage 8 (`stageRouting`, lines 557-620) composes a `RouteRequest` from the five Core routing axes and delegates the route **decision** to the pinned `drenyra-ai` Core `route()` router — Shell does not own a local route table (the prior 18-cell `route-selector.ts` was deleted in the 2026-08-15 rebase per `openspec/changes/archive/2026-08-15-pi-sdd-030-routing-adapter/archive-report.md` lines 186-196).
- `lib/routing/executor.ts` — `executeRoutingWork` maps the Core's `Route.kind` to a Shell execution port via the fixed table (lines 64-68): `"direct-analysis" → "direct"`, `"specialized-agent" → "delegated"`, `"durable-mission" → "durable"`. It dispatches **exactly one** port call (no fallthrough, no retry), verifies the port's response (mission identity, evidence hashes, tool allow-list, consumption shape — `verifyResponse`, lines 178-240), and advances the mission **only** through an injected `CanonicalTransitionValidator` (`validateTransition` from `drenyra-ai/missions`).

### Modality wiring: only "durable" has a production port; "direct" and "delegated" do not

`RoutingExecutionPorts` (types.ts:383-387) is an interface with three functions (`direct`, `delegated`, `durable`) that `executeRoutingWork` receives injected, not constructed itself. Searching the whole repo for implementations of that interface found exactly one production implementation:

- `lib/mission-commands.ts:672-752` — `createDurableMissionRoutingPort(coordinator)` returns `RoutingExecutionPorts["durable"]`. It calls `coordinator.advance({ missionId })` **exactly once** and maps `AdvanceEdaMissionResult` (WAIT / authority-denied / UNKNOWN / normal) into the typed port response.

No file anywhere in the repo — production or test — implements `RoutingExecutionPorts["direct"]` or `RoutingExecutionPorts["delegated"]` against real logic (a real in-process chain run for "direct", or a real subagent dispatch for "delegated"). The only place `direct`/`delegated` ports are populated at all is inside test fixtures that stub them out with a generic counting wrapper:
- `__tests__/routing/routing-adapter-journey.test.ts` (`makePorts`, lines 78-104) — wraps a caller-supplied stub handler for all three port names identically; the "journey" test (the one place SDD #1's `routing-adapter` domain claims end-to-end coverage) only ever exercises the **"direct"** port, and even that is a hand-written `makeSuccessResponse` stub, not real chain-pipeline execution.
- `__tests__/routing/fixtures.ts` builds `PreflightRequest` fixtures but contains no port implementation at all.

### Nothing in production ever calls `executeRoutingWork` or `runRoutingPreflight`

Grep across `extensions/` (the only place `/drenyra:*` command handlers live) for `executeRoutingWork`, `runRoutingPreflight`, `RoutingExecutionPorts`, and `createDurableMissionRoutingPort` returns **zero matches**. Confirmed directly: `/drenyra:mission`, `/drenyra:continue`, `/drenyra:resume` (the only commands that touch `EdaMissionCoordinator`) call `coordinator.start(...)` / `coordinator.advance(...)` **directly** (`extensions/register.ts:684-742`), bypassing `lib/routing/` entirely. `createDurableMissionRoutingPort` itself is invoked only by `__tests__/routing/mission-routing-seam.test.ts` and `__tests__/extension-mission-commands.test.ts:854` — never by a command handler.

**Conclusion**: `lib/routing/` is a correctly-designed, unit/contract-tested library (62 tests from the archived `pi-sdd-030-routing-adapter` change, per its archive-report) sitting completely disconnected from the extension's live command surface. It is exercised by its own test suite and nothing else. This is a materially different (and worse) finding than SDD #1's "advisory-only model-routing registry" — the model-routing registry at least renders informational output when a real command runs; the routing adapter's `preflight → route → execute` pipeline never runs in a live Shell session at all today, under any command.

### Fail-closed / missing-capability behavior is real, but only proven in isolation

The behavior the acceptance bar calls "informs missing capabilities and stops correctly" is genuinely implemented at two layers, uniformly across all three route kinds (not durable-only):
1. Preflight stage 6 (`stageSystems`, `lib/routing/preflight.ts:359-420`) — an unavailable system returns a typed `EXTERNAL_SYSTEM_UNAVAILABLE` stop before any `WorkUnit` is even built. Tested: `__tests__/routing/preflight.test.ts:243-244`.
2. Executor dispatch guard (`lib/routing/executor.ts:409-430`) — an unrecognized `route.kind` returns `AMBIGUOUS_INPUT { fields: ["route.kind"] }` (tested: `__tests__/routing/executor.test.ts:290`), and a missing/non-function port (`typeof port !== "function"`) returns `AMBIGUOUS_INPUT { fields: ["ports.<name>"] }` — this second branch has **no dedicated test** found in `executor.test.ts` (only the sibling `route.kind` branch is asserted).

UNKNOWN-mission halting (already verified in SDD #1) is confirmed identical in this module: an already-UNKNOWN mission is rejected before any port call (`executor.ts:434-444`), and a port moving a mission into UNKNOWN performs zero further port calls (`executor.ts:584-592`, tested by `routing-adapter-journey.test.ts` "UNKNOWN outcome is never retried and never auto-advanced").

So: the fail-closed *code* for missing capabilities is real and modality-agnostic. What's missing is a caller that would ever let an operator observe it — since nothing in production builds a `RoutingExecutionPorts` object with a genuinely absent `direct`/`delegated` port and runs it against a live task.

### "Agents and models connected with budgets" — not demonstrated anywhere

- `agents/` (10 subagent markdown definitions, `agents/README.md`) has **zero code-level connection** to `BudgetLedger` or `lib/routing/`. Agents are prompt/contract definitions consumed by the Pi host's own agent-invocation mechanism (outside this repo's code), with authority ceilings (ANALYZE/PREPARE) enforced by convention in the markdown + `__tests__/agents.test.ts` tool-grant assertions (REQ-AGENT-005) — not by `BudgetLedger` or any routing-adapter code path.
- `extensions/register.ts:1186-1190` `/drenyra:models` — confirmed in SDD #1 as advisory-only ("no Pi model-routing API in this slice"); `capability-manifest.yaml` independently marks `model-routing: partial` with that exact limitation string.
- `BudgetLedger` (the one real, enforced budget mechanism in the repo) has grep hits **only** inside `lib/routing/{types,executor}.ts` and their tests (`__tests__/routing/*.test.ts`, `__tests__/extension-mission-commands.test.ts`) — never inside `agents/`, `extensions/register.ts`, or any model-dispatch code.
- No file in the repo maps a task/phase to a concrete (agent, model, budget) triple that gets enforced at dispatch time. The closest artifact is `BudgetLedger`, which enforces budgets per `WorkUnit`, not per agent or per model — and it is only ever instantiated inside tests.

**Net**: "agents and models connected with budgets" is not met by any single mechanism today. The model-routing registry is advisory prose; the agent definitions carry no budget concept; `BudgetLedger` is real and rigorously fail-closed but is orphaned from both agents and models in production.

### Test coverage: unit/contract only, no live-modality-traversal test exists

- `__tests__/routing/preflight.test.ts`, `executor.test.ts`, `mission-routing-seam.test.ts`, `routing-adapter-journey.test.ts` — all unit/contract-level, in-process, using stub ports and a stub chain (`makeStubChain`, journey test line 44-51).
- No test (found via exhaustive grep of `direct-analysis|specialized-agent|durable-mission` and `RoutingExecutionPorts`) drives **one task** through direct, then delegated, then durable in sequence, or even asserts all three ports are independently reachable with real (non-stub) logic. The journey test's five cases each exercise the pipeline once, and four of five use the "direct" port slot; none exercises "delegated" at all, stub or otherwise, by name (the shared `makePorts` helper wires all three identically but only `direct` is ever invoked in the journey assertions).
- This directly falls short of the acceptance bar's evidence requirement: *"A task traverses each modality"* — no fixture, test, or command demonstrates any single task's modality path being decided by the real Core `route()` for anything other than `direct-analysis`, nor executed through anything other than a stub port (durable is the sole exception, and even there only through direct port-function calls in tests, not through `executeRoutingWork`).

## Affected Areas

- `lib/routing/executor.ts` — dispatch/verification/fail-closed logic is complete; needs a real caller and (if direct/delegated modalities are to be demonstrated) real port implementations.
- `lib/routing/preflight.ts` — complete 8-stage preflight; no changes needed to demonstrate the acceptance bar, only a real caller supplying real `PreflightRequest` data instead of fixtures.
- `lib/mission-commands.ts` — has the only production port (`createDurableMissionRoutingPort`); would need equivalent `createDirect...Port` / `createDelegated...Port` functions (or equivalents elsewhere) if direct/delegated production wiring is in scope.
- `extensions/register.ts` — the actual `/drenyra:*` command surface; `missionHandler` (lines 657-770) currently bypasses `lib/routing/` entirely by calling `EdaMissionCoordinator` directly. This is the file that would need to change to make any modality observable from a live command.
- `agents/README.md`, `agents/*.md` — subagent definitions with no code-level budget or routing-adapter linkage; relevant only if "delegated" is scoped to mean "dispatch to a Shell subagent."
- `capability-manifest.yaml` — has no `routing-adapter` row at all (only `pi-subagents` and `model-routing`, both already flagged as gap-bearing by SDD #1); any capability claim from this change needs a new row with an honest verification level, almost certainly `unit-or-contract-tested` at best, never `validated-end-to-end`.
- `docs/architecture/capability-conformance-matrix.md` — the existing point-in-time matrix (dated 2026-09-09, same day) does not mention `lib/routing/` at all; it would need a new row consistent with the finding above.
- `__tests__/routing/*.test.ts`, `__tests__/extension-mission-commands.test.ts` — existing unit/contract coverage; a new end-to-end/journey-style test would be needed to demonstrate literal multi-modality traversal if that becomes the chosen scope.

## Approaches

1. **Wire real production dispatch for all three modalities and add a genuine one-task, three-modality traversal test.** Build real `direct` (in-process `chain-pipeline` run, no external agent) and `delegated` (dispatch to one of the ten `agents/*.md` roles under its documented ANALYZE/PREPARE ceiling) ports; wire `runRoutingPreflight` + `executeRoutingWork` into a new or existing command path (e.g., replace `missionHandler`'s direct `coordinator.advance()` call, or add a new `/drenyra:route` command); add an integration test that runs one task through direct → delegated → durable across separate calls, asserting budget enforcement and a deliberately-missing capability (e.g., an unregistered port or unavailable system) halting cleanly.
   - Pros: closes the literal acceptance-bar gap; makes the already-correct fail-closed code observable in production; the current code's architecture (Core-delegated route decision, injected validator, verified port responses) doesn't need redesign, only real ports and one real caller.
   - Cons: highest effort; touches a live command path (`extensions/register.ts`) with real behavioral risk (could change what `/drenyra:mission` does today); needs careful non-goal boundaries (no new fiscal authority, no reimplementing Core materiality/route decisions — same REQ-BOUND-001 constraint the archived change already enforced); the "delegated" port's real semantics (which agent, what triggers dispatch, what budget maps to what) is a design decision this exploration cannot make.
   - Effort: High.

2. **Document the gap honestly via a capability-matrix-style addendum and a minimal single-file demonstration, without touching the live command surface.** Add a `routing-adapter` row to the capability matrix stating current state precisely (preflight/executor real and unit-tested; only the durable port has production wiring; direct/delegated ports have zero real implementation; no command ever calls the pipeline); write one new test that drives a single `PreflightRequest` through all three route kinds against the **real** Core `route()` (not the mission-seam stub) with three distinct, still-stubbed-but-distinguishable ports, explicitly proving the routing decision and dispatch selection logic work uniformly — while being explicit in the artifact that this remains unit/contract evidence, not a live-command traversal.
   - Pros: low risk, no production command-surface change, fast; matches the pattern SDD #1 already established (Approach 3 there) of landing an honest point-in-time gap statement rather than overclaiming; avoids inventing "delegated" semantics under exploration-phase time pressure.
   - Cons: does not actually satisfy the acceptance bar's plain-language requirement ("a task traverses each modality... reports missing capabilities and stops correctly") in any observable, real sense — it documents the gap rather than closing it; risks becoming a fourth stale point-in-time artifact if not tied to a concrete follow-up (the exact failure mode SDD #1 already found three times in this repo).
   - Effort: Low.

3. **Middle ground: wire only the smallest real "direct" port (in-process chain execution, no agent dispatch) into one existing read-only command, and leave "delegated" explicitly out of scope with a documented follow-up.** This demonstrates two of three modalities for real (durable already has production wiring via the mission handler path if it's also connected to `executeRoutingWork`; direct gets a first real port), keeps the diff bounded to a read-only/no-mutation command (`requestedEffect: "read-only"` routes to `direct-analysis` per the fixture's own Core route request), and defers "delegated" (which requires a harder design decision about agent dispatch and budget-per-agent) to an explicitly tracked next change.
   - Pros: bounded, reviewable diff; proves the architecture in production for the lowest-risk modality; avoids inventing agent-dispatch semantics under time pressure; still leaves an honest, explicitly-tracked gap for "delegated" and for "agents connected with budgets" rather than silently declaring SDD-030 served.
   - Cons: still does not fully satisfy the acceptance bar (only 2 of 3 modalities become live); needs explicit language that SDD-030 is not being claimed complete (per this change's own directive) and that "delegated" + agent/model/budget wiring is a named follow-up, not forgotten scope.
   - Effort: Medium.

## Recommendation

Approach 3, with an explicit, tracked follow-up for "delegated" — mirroring how SDD #1 explicitly deferred the `capability-manifest.yaml` tooling investment rather than bundling everything into one change, and consistent with this change's own instruction not to claim SDD-030 completion. A full three-modality live wiring (Approach 1) requires an agent-dispatch design decision ("delegated" = which agent, triggered how, budgeted how) that does not belong in exploration and would likely blow the 400-line PR review budget on its own. Approach 2 (documentation-only) under-delivers against the acceptance bar's plain demand for a task to actually traverse modalities and is exactly the kind of "hand-authored snapshot with no forcing function" pattern SDD #1 found three separate instances of already in this repo. Approach 3 makes real, observable progress (one live modality, real fail-closed missing-capability proof against a live command instead of a stub) while keeping the diff bounded and being explicit about what remains open.

## Risks

- The acceptance bar's exact wording ("Una tarea recorre cada modalidad") most naturally reads as *all three* modalities in one demonstrable path. Approach 3 only closes two of three (durable already has a production port; direct gets a new one; delegated stays a documented gap) — this needs explicit user/orchestrator sign-off before `sdd-propose` locks in that reduced scope, since it does not fully satisfy the literal bar as written.
- `extensions/register.ts:657-770` (`missionHandler`) is a live, tested command path (part of the 20-command surface verified in SDD #1). Any change wiring `lib/routing/` into it risks behavior drift for `/drenyra:mission` unless the change is additive (new command) or very carefully scoped to preserve `coordinator.advance()`'s existing one-phase-per-call semantics.
- "Delegated" dispatch to a real `agents/*.md` role is undefined at the code level today — there is no existing subagent-invocation API in this repo to reuse; designing one is itself non-trivial scope that could belong to a separate SDD-030 slice rather than this change.
- `BudgetLedger`'s "per work unit, never transferred" design (types.ts:243-255) does not obviously extend to a notion of "per agent" or "per model" budget without further design; conflating the two in a rushed proposal risks contradicting the existing, already-verified, fail-closed invariant (`assertWorkUnit` throwing on any cross-unit reuse).
- The missing-port branch (`typeof port !== "function"` → `AMBIGUOUS_INPUT { fields: ["ports.<name>"] }`, `executor.ts:421-430`) has no dedicated test today; if this change's scope includes proving "informs missing capabilities," this specific branch should get an explicit test, not just the sibling `route.kind` branch that's already covered.
- Reusing the exact SDD-030 program tag (not inventing a new one) is correct per this change's directive, but the README's own program table line for SDD-030 ("Direct / delegated / durable-mission routing from evidence and risk") is a description Shell does not currently fulfill in production for two of the three words in that sentence — the proposal phase should state this precisely rather than imply routing-adapter existence alone satisfies the description.

## Ready for Proposal

Yes, with one explicit scope decision the orchestrator/user must confirm before `sdd-propose`: whether "a task traverses each modality" must mean all three modalities live in this one change (Approach 1, high effort, requires an agent-dispatch design decision), or whether a scoped two-of-three live demonstration plus an explicit tracked follow-up for "delegated" (Approach 3, recommended) satisfies this change's acceptance bar. Evidence for either path is fully gathered above with concrete file:line citations; no further exploration is needed to make that call.
